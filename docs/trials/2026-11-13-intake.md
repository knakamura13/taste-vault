# Temporary reference intake trial

The user supplied 132 Alarm UI PNGs for temporary testing, explicitly excluding them from the shipped reference library. Sources remained read-only. All database writes and copied files used dedicated disposable databases and `/tmp` storage.

The repeatable `tests/intake-recovery.mjs` suite exercises the built application through `scripts/start.js`, without an explicit `BODY_SIZE_LIMIT` override. It verifies:

- Oversized images, corrupt PNGs, and more than 20 files reject the entire batch.
- An invalid project on the second image rolls back the first inserted reference and removes the first written image file.
- Browser validation retains selected image bytes and draft metadata.
- Removing an oversized first image retains the second image's override as it becomes the first item.
- The intake form fits a 320px viewport with selected files and expanded overrides.
- All 132 original images save through the HTTP form, with byte-for-byte and SHA-256 readback.
- Duplicate rejection adds nothing; explicit confirmation adds a new reference.

Changes accompanying the trial set the standard launcher request limit to 210 MB (explicit environment overrides still win), add client-side size/count validation and individual file removal, and constrain file input width on narrow screens. Server validation remains authoritative. The database and filesystem transaction checks passed with actual failure injection; process termination during a filesystem write remains outside this test's scope.

These local checks do not establish hosted deployment behavior, slow-network performance, or physical mobile-device usability. The temporary images are not shipped fixtures. Run instructions are in README.md.
